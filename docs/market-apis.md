# 마켓 API 문서 및 제약

2026-09-28 조사. **외부 API 는 바뀌므로 구현 직전에 각 공식 문서를 다시 확인한다.**

## ⚠ 가장 중요한 제약: 네이버는 "고객이 키를 입력"하는 방식이 금지다

**출처**: <https://github.com/commerce-api-naver/commerce-api/discussions/3463>
(2026-04-28, 질문자 `welly427` — 외부 SaaS 가 다수 판매자를 연동하려는 절차 문의.
답변자 `commerce-api-naver` = 네이버 커머스API 공식 관리자 계정)

원문 인용:

> **"서비스 제공을 위하여 '내스토어 애플리케이션' 정보를 제공 또는 위탁받아 운영하시는
> 방법으로 서비스를 제공해서는 안됩니다."**

같은 답변이 제시한 공식 경로는 둘이다.

- **커머스솔루션** — 솔루션마켓 입점 → 판매자가 구독
- **API대행사** — 스마트스토어센터에서 판매자가 API대행사로 지정 → 인증 토큰 발급

**근거의 성격**: 이용약관 조항이 아니라 공식 창구의 답변이다. 네이버 공식 입장으로 볼 수 있고
사업 판단 근거로 충분하지만, 약관 조항 자체가 필요하면 커머스API센터에 로그인해 이용약관을
확인해야 한다.

부수 확인 사항 ([Discussion #1582](https://github.com/commerce-api-naver/commerce-api/discussions/1582), 2024-04):
커머스API 문서는 웹페이지로만 제공되고 PDF 전체 안내서가 없다. **리뷰·톡톡 상담 데이터는
커머스API 로 수집이 지원되지 않는다.**

즉 판매자가 자기 Client ID/Secret 을 SellerHub 에 입력하고 우리가 대신 호출하는 구조는
네이버 정책 위반이다. 두 경로만 있다.

| 경로 | 조건 | IP 등록 |
|---|---|---|
| **SELF** (판매자 본인이 자기 스토어를 호출) | 제약 없음 | **필요** — 공인 IP 등록 |
| **커머스솔루션** (솔루션마켓 게시, 판매자가 구독) | 테스트 + 최종 심사 | 불필요 |
| **API대행사** (판매자가 센터에서 대행사로 지정) | **국내 법인 사업자 필수**, 심사 | 불필요 |

사전 검토 절차는 없고, 신청서 내용이 실제 서비스와 일치해야 승인된다.

**SellerHub 에 대한 함의**

- **1차(메리코코 단독)는 문제없다.** 메리코코가 자기 스토어를 호출하는 SELF 경로다. 고정 IP 등록으로 진행한다.
- **외부 판매자로 확장하려면 API대행사 또는 커머스솔루션 등록이 선행돼야 한다.** 리드타임이 길고
  심사 결과가 불확실하므로, 판매자 모집 일정을 여기에 맞춰야 한다.
- 리뷰 API 는 현재 미제공. 정산·API데이터솔루션은 별도 권한 확인 필요.

ESM(G마켓·옥션)도 비슷하다. 판매자가 ESM+ 에서 **판매도구 제공업체**로 SellerHub 를 지정해야 하고,
그러려면 SellerHub 가 판매도구 제공업체로 승인돼 있어야 한다. 승인은 "내부 지원 리소스 한도 내"에서
이뤄지고 거부될 수 있다 (문의 `etapihelp@gmail.com`).

## 적법성 검토 — 고객 키를 받아 대신 호출하는 방식

법률 자문이 아니다. 확정 판단은 변호사 확인이 필요하다.

**"불법"과 "약관 위반"은 다르다.** 네이버의 "허용되지 않는다"는 이용약관·정책상 불허이고
형사처벌 대상이라는 뜻은 아니다. 판매자가 자기 키를 제3자에게 주는 것을 약관이 금지한다면
정보통신망법상 "정당한 접근권한" 성립 여부에 다툼의 여지가 생기지만, 계정 소유자가 자발적으로
제공한 경우라 실무상 형사 문제로 가는 경우는 드물다.

**확실한 법적 의무는 개인정보 처리위탁이다.** 주문 데이터에 주문자 이름·주소·전화번호가 들어가므로
판매자가 개인정보처리자, SellerHub 가 수탁자가 된다. 개인정보보호법상 **위탁계약 문서 체결과
위탁 사실 공개가 의무**다. API 경로와 무관하게 필요하고 빠뜨리면 제재 대상이다.
DB 를 Supabase 서울 리전에 둔 것은 국외이전 절차를 피하기 위한 선택이다.

**실질 위험은 약관 쪽이다.** API 차단(기능 즉시 정지), 판매자 계정 제재(판매자 손해 → 우리 배상 책임),
그리고 네이버가 공개 답변으로 명시해둔 만큼 "몰랐다"가 성립하지 않는다.

**공식 경로가 이미 있고 경쟁 솔루션들이 그 경로로 들어가 있다.** ESM 의 판매도구 제공업체 목록에
기존 솔루션사 이름이 있는 것이 그 증거다. 적법한 경로가 있는데 위반 경로를 갈 이유가 없고,
나중에 정식 등록할 때 이력이 불리해질 수 있다.

**1차(메리코코 단독)는 정식 경로다.** 메리코코가 자기 스토어·자기 쿠팡 계정을 호출하는 구조이고
SellerHub 는 그 사내 도구이므로 제3자 대행이 아니다. 네이버 SELF + 쿠팡 자체개발로 진행한다.

**외부 판매자를 받기 전에 정식 등록이 선행돼야 한다. 이것이 일정의 임계경로다.**
심사 기간이 미지수이므로 1차 개발과 병행해 지금 신청을 시작한다.

### 인증 구조 — 판매자 키를 받을 필요가 없다 (확정)

출처: <https://github.com/commerce-api-naver/commerce-api/discussions/780>

인증 토큰 발급 시 `type` 파라미터가 **접근 가능한 리소스 범위**를 정한다.

| 애플리케이션 | 가능한 type | 접근 범위 | account_id |
|---|---|---|---|
| **내스토어** | `SELF` 만 | 연결된 스마트스토어 **1개** | 불필요 |
| **솔루션** | `SELF` | 솔루션 자체 리소스 | 불필요 |
| **솔루션** | **`SELLER`** | **솔루션을 쓰는 개별 판매자 계정 1개** | **필수** |

일반 판매자는 `SELLER` 를 쓸 수 없다.

**우리 솔루션 애플리케이션 1개로 `type=SELLER` + `account_id` 로 판매자별 토큰을 받는다.
판매자 키를 받을 필요가 아예 없다.**

내스토어 애플리케이션을 받아쓰면 안 되는 이유가 기술적으로도 드러난다 — 그것으로는 `SELF` 밖에
안 되므로 판매자 수만큼 애플리케이션을 관리해야 하는 기형이 된다. 정책 위반이면서 구조적으로도
막힌 길이다.

**스키마에 미치는 영향**: 마켓별로 `channel_account.credential_enc` 에 담기는 값의 성격이 다르다.

| 마켓 | credential_enc 에 담기는 것 | 전역 비밀 |
|---|---|---|
| 네이버 (솔루션) | `account_id` (판매자 식별자) | 솔루션 애플리케이션 ID/Secret — **환경변수** |
| 쿠팡 | 판매자별 accessKey · secretKey · vendorId | 없음 |
| 11번가 | 판매자별 API Key | 없음 |
| 롯데ON | 판매자별 인증 KEY | 없음 |

`credential_enc` 가 JSON 한 덩어리라 스키마는 그대로 쓸 수 있다. 네이버용 전역 애플리케이션
키만 `.env` 에 추가한다.

### 애플리케이션이 세 종류다 — 금지 대상은 '내스토어' 뿐

Discussion #3463 답변의 *"'대행사 애플리케이션'은 '솔루션/내스토어 애플리케이션'과 다르게"* 라는
표현에서 드러난다.

| 종류 | 용도 | 제3자 제공 |
|---|---|---|
| **내스토어 애플리케이션** | 판매자 본인용 | **금지** — 이것이 공식 답변의 대상 |
| **솔루션 애플리케이션** | 커머스솔루션용. 판매자가 발급해 솔루션에 연결 | 정상으로 추정 |
| **대행사 애플리케이션** | API대행사용. 대행사가 1개로 전 판매자 호출 | 정상 |

Discussion #780 으로 확정됐다 — 솔루션 애플리케이션은 `type=SELLER` + `account_id` 로 판매자별
토큰을 받으므로 **판매자 키를 받지 않는다.** 위 「인증 구조」 절 참조.

채널톡이 *"애플리케이션을 생성하고 API ID와 Secret 을 입력"* 이라고 안내하는 것은 구형 방식이거나
SELF 경로일 가능성이 있다. 우리는 SELLER 방식으로 간다.

### 경쟁 솔루션의 네이버 문의 처리 범위

**채널톡** — 공개 문서에 범위가 명시돼 있어 가장 참고할 만하다.

| | |
|---|---|
| 상품 Q&A | 수집·답변 가능 |
| 주문 고객 문의 | 수집·답변 가능 |
| 고객센터 문의 | **수집 안 됨** |
| 톡톡 | 언급 없음 (API 자체가 없다) |

수집 주기 15분, 초기 설치 시 최근 30일치. 답변은 **스마트스토어 Q&A 게시판 답글로 자동 등록**되어
고객이 앱/웹 "내 문의" 에서 확인한다. 주문 데이터 첫 동기화에 약 2일.

→ **제3자 솔루션이 네이버 문의를 수집하고 답변까지 보내는 것이 실제로 작동한다는 증거다.**

**사방넷** — *"다수의 쇼핑몰에 접수된 고객문의를 일괄 수집 및 답변 일괄 송신"* 기능이 있고
홈페이지에 C/S 를 관리 대상으로 명시한다. 다만 **쇼핑몰별 지원 목록이 사방넷 관리 페이지의
`쇼핑몰 관리(지원)` 메뉴 안에 있어 네이버에 대한 구체 범위는 공개 자료로 확인할 수 없다.**
확인이 필요하면 고객지원(1599-1311)에 문의한다.

### 네이버 API대행사 등록 조건

**필수 요건 (둘 다 반려 사유로 명시돼 있다)**

- **국내 법인 사업자** — 문구상 개인사업자는 불가로 읽힌다. **확정 확인 필요**
- 신청서 내용이 실제 제공 서비스로 판단될 수 있어야 한다

**발급 구조 — 지금 아키텍처와 맞는다**

- 사업자등록정보 기준으로 **사업자당 대행사 애플리케이션 1개**
- 대행사 애플리케이션은 커머스API센터에서 **조회되지 않는다** (별도 발급·전달)
- **판매자별 IP 등록 불필요** — SELF 경로의 "최대 3개, 공인 IP만" 제약이 사라진다
- 각 판매자 토큰은 `인증 토큰 발급 요청 API` 로 받는다

대행사 애플리케이션 하나로 모든 판매자를 호출하는 구조이므로, 중앙 서버 +
`channel_account` 에 판매자별 토큰을 보관하는 현재 설계가 그대로 맞는다.

**Rate Limit** — 대행사를 이용하는 판매자가 늘수록 해당 대행사 애플리케이션의 한도가 증가한다.

**커머스솔루션과의 차이**

| | API대행사 | 커머스솔루션 |
|---|---|---|
| 판매자 연결 | 판매자가 스마트스토어센터에서 대행사로 지정 | 솔루션마켓 게시 → 판매자 구독 |
| 심사 | 신청서 검토 | **테스트 + 최종 심사** |
| 법인 요건 | 국내 법인 필수 | 명시 없음 (확인 필요) |

API대행사 쪽이 진입 장벽이 낮아 보인다.

**기술지원 저장소가 역할별로 따로 있다**

- API대행사 — <https://github.com/commerce-api-naver/api-agency>
- 커머스솔루션 — <https://github.com/commerce-api-naver/commerce-solutions>
- 일반 판매자 — <https://github.com/commerce-api-naver/commerce-api>

**직접 확인해야 하는 것** (naver.com 은 외부 조회가 막혀 있다)

1. **개인사업자 가능 여부** — 법인이 아니면 API대행사 경로가 막히고 커머스솔루션으로 가야 하며 심사 단계가 늘어난다. **가장 먼저 확인할 것**
2. **심사 소요 기간** — 일정의 핵심 미지수
3. 신청서 양식·제출 경로 — 커머스API센터 공지사항 (로그인 필요)

셋 다 `api-agency` 저장소 Discussion 으로 물으면 된다. 사전 검토 절차는 없으므로 문의 자체에 부담이 없다.

### "먼저 개발하고 나중에 등록" 은 맞는 순서다 — 단 메리코코 키로

네이버 API대행사 심사는 "신청서 내용이 실제 서비스와 일치해야 승인"이다. 동작하는 솔루션 없이
신청하면 불리하므로 **먼저 개발하는 것이 심사의 전제조건**이다.

```
1차 개발 (메리코코 SELF)  →  정식 등록 신청  →  심사 중 2차 개발  →  승인  →  외부 판매자
```

병목은 개발이 아니라 심사 기간이다. 1차 완성 즉시 신청하고 심사 중에 2차를 개발한다.
심사 소요 기간이 지금 모르는 값이고, 그것이 전체 일정을 결정한다.

**외부 판매자 키를 먼저 쓰는 것은 개발을 빠르게 하지 않는다.** 코드는 같고 메리코코 계정으로
전부 검증된다. 얻는 것은 "승인 전에 판매자 몇 명을 받는다" 하나뿐이다.

### IP 등록이 제3자 대행의 탐지 장치다

외부 판매자 키를 받아 우리 서버에서 호출하려면 그 판매자들의 애플리케이션에 **전부 우리 서버
IP 를 등록**해야 한다. 그러면 마켓 쪽에서는 이렇게 보인다.

```
판매자 A 애플리케이션 — 등록 IP 34.64.120.15
판매자 B 애플리케이션 — 등록 IP 34.64.120.15
판매자 C 애플리케이션 — 등록 IP 34.64.120.15
```

서로 무관한 판매자들이 같은 IP 를 쓰고 있다는 사실이 조회 한 번에 드러난다. 숨길 방법이 없다.
IP 등록을 요구하는 구조 자체가 제3자 대행을 걸러내는 장치다.

| 마켓 | 판매자 키를 받아 대행 호출 |
|---|---|
| 네이버 | **금지** — 대행사 애플리케이션으로 호출해야 한다 (공개 답변) |
| ESM | 판매도구 제공업체를 목록에서 선택 — 목록에 없으면 진입 불가 |
| 쿠팡 | **정상 흐름** — 연동업체 등록 후 판매자 키를 받아 호출한다 |
| 11번가 · 롯데ON | 판매자 키 방식 (IP 등록 필요) |

**네이버만 엄격하다.** 네이버는 대행사가 자기 애플리케이션으로 호출하는 진짜 대행 구조를 요구하고
판매자 키 전달을 금지한다. 나머지는 판매자 키를 쓰는 방식이다.

따라서 위 IP 탐지 문제는 **네이버에 한정된다.** 그럼에도 결론은 같다 — 네이버 때문에 정식 등록이
필요하고 그것이 일정의 임계경로다.

### 쿠팡 연동업체(Integrator) — 쿠팡판 대행사 제도

- 연동업체는 **쿠팡과 이미 제휴한 ERP/솔루션 업체 목록에서 선택**한다. 자유 입력이 아니다
- 목록에 추가되려면 **설문지 작성 + "쿠팡 API 변경 동의"** 로 사전 승인을 받는다
- 키는 **판매자 계정에 발급**되고, 판매자가 솔루션에 전달한다. 연동업체 선택은 쿠팡이 어느
  솔루션과 연동하는지 파악하는 장치다
- 목록에 없으면 판매자가 `자체개발(직접입력)` 로 업체명·URL·IP 를 넣어야 하는데, 이는 판매자
  본인 개발을 전제한 항목이므로 **연동업체 등록이 올바른 경로다**

네이버와의 구조 차이:

| | 네이버 API대행사 | 쿠팡 연동업체 |
|---|---|---|
| 키 주인 | 대행사 애플리케이션 1개로 전 판매자 호출 | 판매자 계정에 발급, 판매자가 전달 |
| 판매자 키 전달 | **금지** | **정상** |
| 승인 요건 | 신청서 검토, 국내 법인 필수 | 설문지 + API 변경 동의 |
| IP 등록 | 대행사는 불필요 | 필요 (자체개발 시 10개) |
| 판매자당 제약 | — | 키 1개, 다른 툴과 병행 불가 |

### 쿠팡 Rate Limit

판매자ID(업체코드) 당 **초당 호출 수 제한**이 있다. 상품 등록·수정·조회, 수량·가격·판매상태
변경 API 가 대상이다. 판매자별 제한이므로 멀티테넌트에서는 계정 단위로 관리해야 하고,
`job` 테이블로 순차 처리하는 현재 구조가 이에 맞는다.

### 쿠팡: 판매자당 키 1개 — 사업적 제약

> OpenAPI 키는 판매자ID 별로 1개만 발급 가능하며, 연동업체 1개와 자체개발 1개를 동시 등록할 수 없다.

**판매자가 이미 다른 셀링툴을 쓰고 있으면 SellerHub 를 추가로 붙일 수 없다.** 기존 툴을 끊고
전환해야 하므로 판매자 유치 난이도에 직접 영향을 준다. 연동정보 수정은 주당 10회 제한.
키 발급 후 사용까지 최대 24시간 이상 걸릴 수 있다.

## IP 등록 — 고정 IP 는 전제다

| 마켓 | IP 등록 | 등록 가능 개수 | 근거 |
|---|---|---|---|
| 네이버 (SELF) | **필수** | **최대 3개** | IP 미입력이면 인증 토큰 발급이 안 된다 |
| 네이버 (솔루션·대행사) | 불필요 | — | Discussion #3463 |
| 쿠팡 | **필수** | **최대 10개** (자체개발) | 미등록 IP 는 `403 [FORBIDDEN] Not allowed IP` |
| 11번가 | **필수** | 확인 필요 | `Seller API 정보 수정` 에서 입력 |
| 롯데ON | **필수** | 복수 (세미콜론 구분) | IP 등록 후 키 발급 |
| G마켓·옥션 | 미확인 | — | 판매도구 제공업체 지정 방식 |

**유동 IP 는 쓸 수 없다.** 번거로운 수준이 아니라 동작하지 않는다.

- 쿠팡은 **등록 IP 수정을 월 10회로 제한**한다. 유동 IP 가 하루에 여러 번 바뀌면 11번째부터
  다음 달까지 API 를 못 쓴다.
- 네이버는 IP 가 등록돼 있지 않으면 인증 토큰 발급 자체가 실패해 주문 수집이 멈춘다.

**등록 슬롯을 남겨둔다.** 네이버 3개, 쿠팡 10개를 쓸 수 있으니 예비 IP 를 함께 등록해두면
서버 교체·리전 이동을 무중단으로 할 수 있고 쿠팡의 월 10회 수정 한도를 소모하지 않는다.
단 GCP 고정 IP 는 실행 중 인스턴스에 붙어 있을 때만 무료고, 유휴 예비 IP 는 시간당 과금된다
(월 약 7천원).

## 경쟁 솔루션 가이드에서 얻은 API 특이사항

마켓 공식 문서보다 솔루션들의 연동 가이드가 실무 함정을 잘 드러낸다.

### ESM — 셀링툴 5개까지, 단 마스터 ID 단위

- **셀링툴 선택 시 상품/주문 각각 최대 5개**까지 등록 가능 (이지어드민 헬프).
  쿠팡(판매자당 키 1개)과 정반대다. **판매자가 기존 툴을 끊지 않고 SellerHub 를 병행할 수 있다** —
  영업 난이도가 쿠팡보다 낮다
- 경로: `ESM > ESM+계정(ID)관리 > 셀링툴 관리`
- **ESM Master ID 와 연동된 모든 판매자 계정(ID)에 동일한 API 설정이 적용된다.**
  계정별로 다르게 둘 수 없다 → 우리 `channel_account` 의 다중 별칭 설계와 부딪힐 수 있다.
  2차에서 ESM 어댑터를 만들 때 확인한다

### 11번가 — 사전 승인이 없는 유일한 마켓으로 보인다

- **호스팅사를 "직접 입력"** 할 수 있다. 목록에 없어도 진입 가능해 쿠팡의 "자체개발"과 비슷하다
- **IP 입력란이 3종류**: 개발서버 IP / 개발자 PC / 상용서버 IP.
  IP 를 입력해야 셀러 API Key 승인이 난다
- **CS API 에 구매후기(리뷰)가 포함된다** — *"판매자문의/구매후기/CS문의 등"*.
  네이버는 리뷰를 API 로 못 가져오는데 11번가는 된다. 마켓별 격차가 크다
- **주소지·발송마감 템플릿을 상품등록 전에 구성해야 한다**
- 다중 사업자는 스토어 계정마다 API 를 추가 설정한다

### 템플릿 참조가 스키마에 빠져 있다

네이버와 11번가 모두 **배송 템플릿·발송마감 템플릿·주소지를 마켓 쪽에 미리 만들어두고**
상품등록 시 그 템플릿 ID 를 참조하는 방식이다. 지금 `channel_product` 에는 그런 필드가 없다.
상품등록 단계에서 `channel_account` 에 템플릿 ID 를 보관하는 구조가 필요하다.

### 상세설명 HTML 은 escape 처리가 필요하다

홑/쌍 따옴표가 JSON 구문을 깨뜨린다. 사소해 보이지만 상품등록 실패의 흔한 원인이다.

### 카테고리는 일대일 매칭 테이블로 관리한다

업계 공통 방식이다. 마스터 카테고리 ↔ 마켓 카테고리를 미리 매칭해두고 등록 시 그 값을 보낸다.
마스터 카테고리가 70% 만 채워져 있으므로 매칭표를 만들기 전에 카테고리 보강이 필요하다.

### 시장 가격대 — 인프라 정상가는 문제가 아니다

| | 연동 채널 | 월 가격 |
|---|---|---|
| 사방넷 | 250~600 (출처별 차이) | 25만원 (발주 3천건) |
| 이지어드민 | 50 | 20만원 (발주 3만건) |
| 플레이오토 | 100 | 16만원 (발주 1만건) |

사방넷이 셀러 약 7,000곳, 점유율 80% 수준. **월 16~25만원 시장이므로 인프라 정상가가 판매자당
1만원 이하면 마진 구조는 충분하다.** 비용 때문에 설계를 비틀 이유가 없다.

`smartstore-order-desk` 의 송장 전송 4상태 구분은 우리 `shipment.dispatch`(PENDING/SENT/FAILED)보다
세밀하다. "성공 응답을 받았지만 마켓 반영은 아직 확인 못 함" 상태가 실제로 필요한지 구현 때 판단한다.

## 저장소에 있는 참고 자료

`commerce-api-naver` 조직은 저장소가 셋이고 역할이 갈린다. **문의는 해당 저장소로 해야 한다.**

| 저장소 | 대상 |
|---|---|
| `commerce-api` | 일반 판매자 (★117) |
| `commerce-solutions` | 커머스솔루션 개발사 (★18) |
| `api-agency` | API대행사 — 설명에 *"커머스API **테스트 버전** 연동"* |

`api-agency` 설명의 "테스트 버전" 표현이 대행사 제도가 아직 테스트 단계임을 시사한다. 확인 필요.

**`commerce-api` Wiki** (본문 유지됨):

- `[주문] 주문 상태 변경 흐름도` — 정상·취소·반품·교환 4가지 흐름 다이어그램.
  **주문 상태 State Machine 설계 시 반드시 볼 것** (내용이 이미지라 텍스트 추출 불가)
- `[가이드] N배송 SKU 상품 관리 가이드`
- `스마트스토어 상품 가이드`
- `커머스API 그룹상품 연동 가이드`

**`commerce-solutions` Wiki** (2024-10-16 부로 본문 비워짐, 제목만 남음 — 내용은 apicenter 로 이전):

```
[가이드] 솔루션사 커머스API 인증 토큰 발급
[가이드] 커머스솔루션 사용자 식별자 연동 및 사용 해지 프로세스
[가이드] 커머스솔루션 마켓 요금제 가이드          ← 수수료·정산 구조
[가이드] 판매자 인증 JWE 구성요소 및 해석
[가이드] 솔루션 사용자 JWT 구성요소 및 연동 주의사항
[가이드] 커머스솔루션에서 발송되는 이벤트훅 호출 규격   ← Webhook 지원
[가이드] 솔루션 회차 및 결제 구조
[가이드] 커머스ID 인증 연동 자체 점검 리스트
[가이드] 기타 연동 시 주의사항 및 참고사항
```

**이벤트훅 규격이 있다는 것이 중요하다.** 요구사항 11번은 Polling 기반을 전제했지만, 커머스솔루션
경로에는 Webhook 이 있다. 폴링 주기를 줄이거나 없앨 수 있다.

**FAQ 색인** (<https://github.com/commerce-api-naver/commerce-api/discussions/1>) 에서 구현 전에
읽어야 할 항목들:

- 인증 토큰: SELF/SELLER 차이, 스토어별·애플리케이션별 발급, 유효 시간, Timestamp 오류
- API 호출: 사용량·호출 제한, 401/BAD_REQUEST/GW.AUTHN 오류, **'호출이 허용되지 않은 IP' 해결**
- 상품(15항목): **원상품과 채널상품 차이**, 이미지 업로드 실패, **인증정보 수록(KC·어린이제품·친환경)**, 카탈로그 연결
- 주문(25항목): **배치성 주문 수집 방법**, 변경 상품 주문 내역 조회 설계, 부분 취소·클레임, **할인금·배송비 계산**
- 정산(2항목): 기준일·예정일·완료일 차이

「원상품과 채널상품 차이」는 우리 `master_product` ↔ `channel_product` 분리와 같은 개념이다.
「배치성 주문 수집 방법」은 폴링 설계에 직결되고, 「할인금·배송비 계산」은 Pricing 에 직결된다.

## 다시 확인할 것

- 쿠팡 Rate Limit — 문서 상세 페이지 또는 키 발급 시
- 11번가 IP 등록 가능 개수
- ESM 의 IP 등록 요구 여부
- **솔루션 애플리케이션을 판매자가 발급해 솔루션에 입력하는 흐름이 맞는지** (채널톡 사례 기반 추정)
- 사방넷의 네이버 문의 지원 범위 (쇼핑몰별 지원 목록은 비공개)
- 네이버 API대행사 신청 요건과 소요 기간 (외부 판매자 확장 일정의 전제)
- ESM 판매도구 제공업체 등록 가능성 — 거부될 수 있으므로 2차 계획의 위험 요소
- 각 마켓 폴링 권장 주기
