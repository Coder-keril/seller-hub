# 심사 전 체크리스트 | 커머스API

On this page
심사 전 체크리스트
아래 모든 항목에 대해 인지 및 구현 후 심사 요청을 해야 합니다.

이러한 체크 리스트는 솔루션 브랜딩, 솔루션 구독, 품질 등 솔루션 사용자에게 최고의 경험을 제공하기 위함입니다.

❗️체크리스트는 커머스솔루션마켓이 업데이트됨에 따라 변경될 수 있습니다.

솔루션은 모든 요구 사항을 충족 해야 하며 충족하지 못했을 경우, 심사 반려될 수 있습니다.

또한, 정기 모니터링을 진행하며 요구 사항에 충족되지 못한 앱은 커머스솔루션마켓에서 미노출 처리 및 수정이 요구될 수 있습니다.

1. 솔루션의 메타 정보 점검​

솔루션의 타이틀, 소개 문구, 이미지, 키워드 정보가 모두 올바르게 기입되어야 합니다.

사용 플랜의 이름, 설명, 금액은 모두 올바르게 설정해야 합니다.

솔루션 사용자가 이용가능한 CS문의 채널은 올바르게 표시해야 합니다.

솔루션 사업자 정보는 유효해야 하며 개발업체 정보 내 이메일 주소를 개인 이메일로 기재되면 안됩니다.

2. 기본적인 보안 의무 준수​

모든 커머스API를 호출하기 위한 애플리케이션 ID(Client ID)와 Secret은 안전하게 관리해야 합니다.

시그니처 생성을 포함한 커머스API 호출에 필요한 모든 작업은 제 3자의 접근이 불가능한 솔루션 시스템의 백-엔드 서버에서만 진행되어야 합니다.

커머스ID 인증창을 호출하는 페이지의 도메인과, 마켓에 등록한 JWE 리다이렉트 URL의 도메인과 항상 일치 되게끔 관리해야 합니다.

커머스ID 인증창을 호출하는 경우, 화면은 iframe을 사용하지 않고 구현해야 하며 OAuth 인증의 표준 구조를 따라 네이버에서 제공하는 로그인 팝업을 통해 사용자의 인증이 수행되도록 구현해야 합니다.

사용자가 위탁한 판매자 또는 구매자의 개인정보, 그리고 중요 식별자(ex. accountUid) 등은 보안 처리 된 환경에서 안전하게 관리해야 합니다.

네이버 스마트스토어 판매자의 ID, 비밀번호 등의 사용자 식별정보를 수집하는 등,  '네이버 계정 운영정책' 을 위반하지 않도록 구현해야 합니다.

판매자가 솔루션 구독을 해지 및 강제해지 발생시 판매자와 판매자 스토어로부터 획득한 구매자의 개인정보, 민감정보, 식별자 정보를 삭제 해야 합니다.

3. 커머스ID 인증 프로세스 점검​

'판매자 커머스ID 인증(이하 '커머스ID 인증')'을 호출하는 화면은 iframe을 이용하여선 안됩니다.

OAuth 인증 표준 구조에 맞춰 네이버에서 권장하는 팝업 창을 통해 사용자의 인증이 수행되도록 구현해야 합니다.

마켓에서 솔루션을 사용중인 이용자가 솔루션 서비스 페이지에서 로그인해야 하는 경우 어렵지 않게 로그인 할 수 있어야 합니다.

사용자가 커머스ID 인증 프로세스로 자연스럽게 이동해야 합니다.

사용자에게 커머스ID 인증창을 팝업 창으로 표시하고 리다이렉트 URL로 JWE 토큰을 수신해야 합니다.

<커머스ID 인증 팝업을 호출하는 페이지 도메인>과 사전에 등록한 <JWE 토큰을 수신하는 리다이렉트 URL 도메인>이 항상 일치해야 합니다.

'판매자 인증 JWE 해석 API(이하 'JWE 해석 API')'를 통해 해석된 신청 사용자 정보를 획득할 수 있어야 합니다.

JWE 토큰의 유효시간은 최초 생성으로부터 72시간이며 JWE 해석 API로 토큰의 해석을 요청하는 시점의 최신 사용자 정보 및 신청 정보가 반환됨을 인지해야 합니다.

JWE 해석 API로 제공하는 accountAuthentication 필드 값을 이용하여 신청 사용자에 대한 커머스API 호출이 가능한지 판별하는 과정이 포함되어야 합니다.

JWE 해석 API로 제공하는 approveSubscriptionYn 필드 값을 이용하여 신청 사용자에 대한 솔루션 사용 승인이 가능한지 판별하는 과정이 포함되어야 합니다.

JWE 해석 API는 API 호출 시점의 사용자 신청 정보가 반환됩니다. '사용 시작 승인 API' 호출 전 대상 사용자의 신청 정보가 승인 가능한 상태인지 확인해야 합니다.

JWE 해석 이후 사용자의 '사용 시작 승인 API' 호출이 불가능 할 때 사용자에게 승인 불가 사유를 적절하게 안내해야 합니다.

커머스솔루션마켓에서의 솔루션 사용 신청을 하지 않았다면 먼저 커머스솔루션마켓에서의 사용 신청이 필요함을 안내

사용자가 대상 스마트스토어의 주매니저 이상의 권한을 보유하지 않은 경우 솔루션 사용을 위한 필요 권한을 안내

그 외 다른 오류코드 및 상황에 알맞은 안내

단, 사용을 신청한 사용자가 솔루션 사용이 불가함이 명확하게 판단될 경우, 거절 사유를 포함하여 '사용 시작 거절 API' 호출하여, 사용자를 '사용 취소' 상태로 변경 가능

'사용 시작 승인/거절 API' 호출 없이 판매자의 사용 신청 90일이 경과되면, 커머스솔루션마켓에서 자동으로 사용자의 솔루션 사용 신청을 거절 처리됨 인지 필요

'사용 시작 승인 API'는 대상 사용자가 솔루션 이용에 필요한 모든 사전 준비과정이 완료 되는 시점에 호출되어야 합니다.

개발사 자체 테스트 계정을 이용하여 ①'사용 시작 승인 API' 호출로 사용 승인을 완료하고 ②스마트스토어센터 내 솔루션 사용 승인 완료 알림을 수신함을 확인해야 합니다.

커머스솔루션마켓 기준으로 솔루션 해지 후 다시 솔루션 사용 신청을 한 사용자가 이전에 커머스ID 인증을 수행하였더라도 또다른 사용 신청에 대한 커머스ID 인증을 최초 1회 수행하도록 설계해야 합니다.

커머스API 호출 시 사용자 식별자인 accountUid 값은 아래 2가지 중 어떤 방법으로 처리하도록 설계해야 합니다. (택 1)

솔루션 시스템 데이터베이스 내에 accountUid 값을 저장 (DB저장방식)

판매자 인증 JWE 토큰을 매 번 수신하여 필요할 때마다 JWE 해석 API 호출 (JWE식별방식)

4. 커머스API를 통한 스마트스토어 이용자 정보 호출 사유 점검​

솔루션 서비스에 이용하려는 API그룹은 적절한 사유가 존재해야 하며 불필요한 API 그룹을 사용해선 안됩니다.

5. (기존에 이미 솔루션을 운영중인 경우) 커머스ID 인증 프로세스 점검 - 기존 사용자  (관련 문서)​

커머스ID인증형 솔루션 전환 후 기존 사용자가 최초 이용 시, 최소 1회 커머스ID인증이 진행될 수 있도록 구현해야 합니다.

기존 사용자에게 커머스ID인증이 왜 필요한 지 적절한 안내를 진행해야 합니다.

사용자 식별자인 accountUid를 정상적으로 활용할 수 있도록 개발해야 합니다.

커머스ID 인증을 완료한 사용자의 스마트스토어를 대상으로 API 호출을 진행할 때에는 "커머스API(/external/...)"로만 정상 호출이 가능합니다.

기존 "제휴API(/partner/...)" 또는 "커머스API 테스트 버전(/partner/...)"을 사용하고 있었다면 커머스ID 인증 여부에 따른 호출 경로 전환 또는 변경 대응이 가능하도록 설계해야 합니다.

커머스ID인증형 전환 배포 직후, 즉시 테스트할 수 있도록 사용중인 테스트용 회원을 충분히 확보해야 합니다.

6. (기존에 대행사 메뉴를 통한 API연결 케이스가 있는 경우) 기존 대행사 메뉴를 통한 API연결 안내 제외​

솔루션 사용자의 혼선을 방지하기 위해, 기존 API 연결 방식은 지양하고 있습니다. 스마트스토어 내 스토어 관리 메뉴를 통한 API연결과 관련한 불필요한 기능은 노출되지 않도록 처리해야 합니다.

판매자 정보 연동을 위한 가이드 등, 사용자에게 가이드로 제공되는 안내 문서도 커머스솔루션마켓을 통한 연동으로 내용이 모두 수정되어야 합니다.

7. 이벤트 훅 스펙 점검​

이벤트 훅을 수신하기 위해 사용하는 URL은 개발하신 서비스 홈페이지의 도메인과 동일한 도메인이어야 합니다.

수신하도록 설정한 모든 이벤트 훅이 누락없이 준 실시간으로 수신되는 지 테스트를 해야 합니다.

이벤트 훅 안에 포함된 accountUid로 사용자를 식별할 수 있어야 합니다.

이벤트 훅에 포함된 각종 일시(date&time)는 UTC+0 시간대 기준임을 확인해야 합니다. (한국 표준시는 UTC+9)

하나의 이벤트 훅 호출 내에 여러 이벤트 정보를 배열(array) 형태로 수신가능하도록 구현되어야 합니다.

몇몇 이벤트 훅의 경우 솔루션 서비스에서 추가 처리가 필요할 수 있습니다. 이벤트 훅 수신 내용에 따라 적절하게 서비스가 구동되고, 사용자에게 안내되도록 구현되어야 합니다.

예 : 강제 해지 이벤트 훅을 수신하면, 관리자 해지 사유를 확인하고 사용자의 서비스 이용을 해지하거나 필요한 경우 담당자를 통해 이슈를 팔롭합니다.

같은 요청이 여러 번 들어오더라도 한 번만 처리되도록 멱등성있게 구현되어야 합니다.

솔루션 시스템이 이벤트 훅의 정상 수신(HTTP 200 OK)을 바로 응답하지 못하는 실패 상황 발생 시 이후 발행되는 이벤트 데이터는 대기 상태로 전환되며 이벤트 훅 발송을 재시도합니다.

이러한 상황 발생 시 상황을 탐지하고 솔루션에서 대응 가능한 매커니즘을 구현해야 합니다.

8. (비즈월렛 유료 솔루션) 이벤트 훅 및 솔루션 사용자 요금 결제 정보 연동에 대한 스펙 점검​

일관적인 '네이버페이 비즈월렛(이하 '비즈월렛')' 사용자 경험을 헤치지 않도록 아래 내용을 준수하여 구현해야 합니다.

커머스솔루션마켓 사용자에 대해 서비스 이용을 위한 요금 지불 과정에서 비즈월렛 외 결제 수단을 제공하여선 안됩니다.

솔루션 서비스 영역에서 솔루션 이용을 위한 추가 결제를 유도하는 기능은 제공하지 않아야 합니다.

이벤트 훅 데이터로 사용자 식별정보(accountUid), 사용자의 이용중인 요금제 고유정보(plan.id)가 함께 전달됩니다. 이 2개 값을 식별하여 처리하고 관리해야 합니다.

솔루션 서비스 영역에서 사용자가 선택한 요금제 정보, 이용금액 등을 포괄하는 유료 결제 정보는 명확하게 안내하도록 구현되어야 합니다.

①요금제 이름과 ②이용금액이 동일하더라도 요금제 고유정보(plan.id)가 동일하지 않다면 서로 다른 별개의 요금제로 인지하여 취급하도록 설계해야 합니다.

솔루션 서비스 제공에 필요한 커머스API를 모두 연동하였으며,테스트 호출 시 모두 성공 응답(HTTP 200 또는 204 응답)을 받아야 합니다.

비즈월렛 결제 내역 조회 API

사용 상태 조회 API

사용 중지 환불 API

사용 시작 승인 API (커머스ID 인증형 솔루션인 경우 필수)

판매자 인증 JWE 해석 API (커머스ID 인증형 솔루션인 경우 필수)

'사용 시작 승인 API' 호출 후 성공 응답(HTTP 200)을 받지 못한 경우 반환되는 응답 내용을 기반으로 사용자에게 통상적인 승인 실패 사유와 더불어 아래 비즈월렛 관련 안내를 명확하게 가이드하도록 설계해야 합니다.

사용자의 비즈월렛 잔액이 부족한 경우 → 비즈월렛 잔고를 충전하도록 안내 (비즈월렛 잔고 충전 링크 표시)

솔루션 사용 신청 상태가 아닌 경우 → 커머스솔루션마켓에서 솔루션 사용 신청을 먼저 하도록 안내 (솔루션 상세 페이지 링크 표시)

솔루션의 유료 회차 시작 시점에 사용자가 선택한 요금제의 이용금액 만큼 테스트 계정의 비즈월렛 잔액이 차감되는지 자체적인 테스트로 확인해야 합니다.

솔루션 서비스 영역에서 사용자가 솔루션 사용을 해지하거나 회원 탈퇴를 진행하는 경우 '사용 중지 환불 API'를 호출하여 커머스솔루션마켓-솔루션 시스템 간 사용 해지 정보를 동기화하도록 자체 테스트로 검증해야 합니다.

이용 중 해지에 대한 솔루션 개발사 정산 및 사용자의 환불은 '사용 중지 환불 API' 호출 시 성공 응답(HTTP 200)을 반환하는 경우 처리 성공 일자를 기준으로 일할 계산합니다.

'사용 중지 환불 API' 호출로 솔루션 사용이 해지되는 경우 이벤트 훅 데이터는 '강제 해지(FORCE_UNSUBSCRIPTION)' 유형으로 전달됩니다.

커머스솔루션마켓은 심야 특정 시간대에 배치 작업으로 회차 사용 시작, 요금제 변경 등의 결제 처리 관련 이벤트 훅 데이터를 대량으로 발송합니다. 대량으로 발생하는 이벤트 훅 데이터를 이상없이 수신하여 처리하고 개별 사용자에게 정확하게 서비스를 제공하도록 설계해야 합니다.

이벤트 훅으로 수신하는 이벤트 유형 중 <결제 성공(PAYMENT_SUCCESS)>과 <회차 시작(START_ROUND)>은 의미하는 바가 다르며 결제 조건에 따라 시차를 두고 발생할 수 있습니다. 또한 사용자에 대한 솔루션 유료 서비스 제공 개시는 <회차 시작(START_ROUND)> 이벤트 발생 시점을 기준으로 해야합니다. 이러한 내용을 명확하게 인지하고 있으며 솔루션 연동 내용에 모두 반영해야 합니다.

이벤트 훅으로 사용자의 <솔루션 해지(END_SUBSCRIPTION)> 혹은 <솔루션 강제 해지(FORCE_UNSUBSCRIPTION)> 데이터를 수신한 경우 솔루션 서비스 영역에서는 즉각 유료 서비스 제공을 중단하고 해지 사용자에게 유료 서비스 제공이 중단되었음을 안내하도록 구현해야 합니다.

요금제 업그레이드가 발생한 경우 즉시 사용자에게 업그레이드 된 요금제의 서비스로 변경하여 제공해야 합니다.

요금제 다운그레이드가 발생한 경우 다음번 사용 회차부터 사용자에게 다운그레이드 된 요금제의 서비스로 변경하여 제공해야 합니다.

커머스솔루션마켓에서 발송하는 모든 이벤트 훅 데이터는 항시적으로 수신 및 처리 상태를 유지할 수 있어야 합니다. 다만, 수신 및 처리 불가가 불가피한 상황에서는 이에 알맞은 200 OK 이외의 HTTP 응답 코드를 반환할 수 있어야 합니다.

이벤트 훅은 그 데이터 양과 수신 빈도가 솔루션 사용자 수에 비례합니다. 개발사에서 예상하는 기대 사용자 수를 감안한 이벤트 훅의 최대 수신 시나리오에서의 부하 테스트 수행 방법 및 경과, 수행 결과를 서술해주셔야 합니다.

이벤트 훅 수신에 실패하는 상황이 발생한 경우 문제를 해결하고 시스템 다운 시간동안의 데이터 변경 처리를 따라잡을 수 있도록 구현해야 합니다.

이벤트 훅 수신 및 처리에 실패하는 상황 발생 시 솔루션 시스템이 이를 자체적으로 탐지하여 솔루션 담당자가 즉각 인지할 수 있어야 합니다.

이벤트 훅 수신 및 처리 실패는 최대한 빠른 시간내 복구를 완료하여야 합니다.

복구 후 '사용 상태 조회 API', '비즈월렛 결제 내역 조회 API' 등을 활용하여 최신 정보로 업데이트 할 수 있도록 구현하여야 합니다.

시스템 다운 시간동안의 변경 데이터는 관련 API를 이용하여 빠짐없이 모두 처리하여 커머스솔루션마켓-솔루션 간 동기화를 완료하여야 합니다.

커머스솔루션마켓 또는 솔루션 시스템의 점검/장애 등으로 10분 이상 솔루션 유료 서비스 제공이 불가능하거나, 이벤트 훅 수신 처리를 할 수 없을 경우 네이버와 소통 가능한 솔루션 측 핫라인 담당자를 확보해야 합니다.

사용자가 이용중인 서비스 요금제를 변경하고자 할 경우 솔루션 서비스 영역에서 커머스솔루션마켓으로 이동할 수 있는 링크를 제공해야 합니다.

9. (조건부 해지 유형의 솔루션인 경우 필수) 조건부 해지 스펙 점검​

판매자가 해지 요청 상태가 되면 '해지 요청(REQUEST_UNSUBSCRIPTION)' 이벤트 훅을 발송합니다. 이 이벤트 훅을 수신해야 합니다.

커머스솔루션 API의 '사용 해지 승인 API'는 판매자의 구독 상태가 '해지 요청' 일 때에만 호출할 수 있음을 인지하고 있어야 합니다.

커머스솔루션 API의 '사용 중지 환불 API'를 호출하면 해지 요청 여부와 관계 없이 즉시 해지가 완료됨을 인지하고 있어야 합니다.

사용자의 편의를 위해 해지 요청은 가능한 한 7영업일 내에 해지 승인 되어야 합니다. 현재 해지 요청을 승인하기까지 걸리는 평균 대기시간과 가장 긴 대기시간은 얼마나 길 지 확인해야 합니다.

테스트 회원으로 해지 요청 이벤트 훅 수신부터 ~ 해지 승인까지, 해지 요청 케이스를 최종 점검해야 합니다.

11. 그 외 장애 및 예외상황 대처 점검​

커머스ID 인증 프로세스가 점검 중 또는 장애 중일 때 API센터에 등록된 장애대응 이메일로 안내를 해 드립니다. 이 때 솔루션 내에서 신속하게 적절한 UX로(또는 장애 안내) 전환하여 표시할 수 있어야 합니다.

예를들어 3분 동안 50%호출 실패와 같은 API 등에서 일정 비율 이상의 지속적인 에러가 발생할 때, 자체적으로 장애여부를 판단하여 적절한 UX로(또는 장애 안내) 전환하여 표시할 수 있어야 합니다.

연동과 관련하여 중요한 정보를 처리하는 API에서 타임아웃이 발생할 경우, 사용 현황 조회 API를 통해 유저 연동상태 확인 및 필요 시 '사용 중지 API' 호출 및 '사유' 안내를 통해 유저 혼선을 방지할 수 있어야 합니다.
